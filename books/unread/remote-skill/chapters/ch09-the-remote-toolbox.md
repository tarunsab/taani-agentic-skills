# Chapter 9: The Remote Toolbox

## Core Idea

The toolbox is a source-era inventory of the kinds of software and places 37signals used to make remote work practical. The important pattern is not loyalty to one vendor; it is a small set of capabilities: a shared project home, screen sharing, reliable voice/video, persistent informal chat, shared files and documents, and access to physical coworking space. Each tool should reduce a specific coordination cost—lost context, delayed feedback, missing social contact, or lack of a workable place to sit. The list reflects the book’s 2013 publication context, so current products and security practices should be reassessed before adoption. The durable lesson is to assemble a coherent system rather than collect tools without changing the workflow.

## Frameworks Introduced

- **Capability-first tooling**: Select tools by the remote problem they solve, not by brand familiarity.
  - When to use: When building or refreshing a distributed team’s toolset.
  - How: Cover project memory, visual collaboration, communication, social cohesion, shared documents, and physical workspace.
- **Single project home**: Keep discussions, tasks, schedules, files, and decisions in a place the whole team can access.
  - When to use: When work is scattered across private inboxes and local machines.
  - How: Make the shared project space the default record of work.
- **Tool-to-mode matching**: Use each medium for the interaction it handles best.
  - When to use: When chat, calls, documents, and meetings are competing for every question.
  - How: Use persistent artifacts for durable context, screen sharing for visual work, calls for immediacy, and chat for informal or short exchanges.

## Key Concepts

- **Project home**: The shared place where work, decisions, files, and schedules remain findable.
- **Screen sharing**: Live visual collaboration around the same digital object.
- **Persistent chat**: A group room that supports informal connection and asynchronous entry and exit.
- **Shared document**: A common, current version of a document, spreadsheet, or presentation.
- **Cloud file store**: A synchronized repository available across devices and locations.
- **Coworking space**: A physical remote-work option between home and a conventional office.
- **Source-era tool**: A product named in the 2013 book whose current availability, features, or security should not be assumed.

## Mental Models

Think of the toolbox as a **coordination stack**: durable project memory, visual context, fast conversation, social connection, and physical workspace solve different failures. Think of the **artifact as the source of truth**: tools are useful when they leave accessible records. Think of **capability before vendor**: a product can be replaced if the operating function remains.

## Anti-patterns

- **Tool shopping without workflow**: Adding apps while leaving decisions and files scattered.
- **One medium for every need**: Using meetings, chat, or email indiscriminately.
- **Vendor permanence**: Treating a product named in a 2013 book as a current recommendation without checking it.
- **Private source of truth**: Keeping the only copy of a task, decision, or file on one person’s machine.

## Source-era toolbox

| Capability | Tools named in the book | Use in the remote system |
|---|---|---|
| Project home | Basecamp | Discussions, tasks, calendars, files, brainstorming, and recorded decisions |
| Screen sharing | WebEx, GoToMeeting, Join.Me | Product demos, show-and-tell, and live work review |
| Company awareness | Know Your Company | Surfacing unspoken views about culture, leadership, and management |
| Voice/video | Skype, Google Hangouts | International calls, conference calls, video, and some screen sharing |
| Quick exchange | Instant Messaging | Short, one-to-one text conversations |
| Persistent social chat | Campfire | Informal connection, shared events, and questions |
| Shared files | Dropbox, SkyDrive | Central files synchronized across devices |
| Collaborative documents | Google Docs | Shared current versions of documents, spreadsheets, and presentations |
| Physical workspace | Regus, LiquidSpace, Desktime, Coworking Wiki | Day offices, hot desks, sublets, and coworking options |

## Practical application

Start by listing the failures the team experiences: waiting for context, describing screens, losing decisions, feeling socially detached, or lacking a suitable place to work. Assign one durable capability to each failure and test whether the tool leaves a record the whole team can find. Keep the project home and shared files authoritative, move visual work onto shared screens or recordings, and reserve calls and chat for the interaction they actually improve. Revisit any source-era product, especially around account security, privacy, authentication, retention, and export.

## Worked Example

The book’s own stack used Basecamp as the project home, GitHub for code and code discussion, shared calendars for availability, WebEx for screens, Campfire for social chat, and ordinary email, phone, and instant messaging for other modes. The stack worked because each tool had a clear role and the important material was open to the team. Reproducing the vendor names is less important than preserving the separation of durable project memory, visual context, fast interaction, and social connection.

## Key Takeaways

1. Choose capabilities before products.
2. Make the shared project space the default memory of the work.
3. Use screens and recordings for visual collaboration and durable context.
4. Keep social chat separate enough that it provides connection without becoming the project record.
5. Treat all named products as historical examples and re-check current security and fit.
